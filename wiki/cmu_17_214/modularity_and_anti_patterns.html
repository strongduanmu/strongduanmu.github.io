模块化与反模式

测试全绿，结构仍可能阻碍变化

上一讲我们通过候补晋升比较职责与耦合。本讲继续看一种常见情况：功能已经通过测试，但打开代码后，仍然很难判断下次修改应该放在哪里。代码异味（Code Smell）为这类值得调查的症状提供名称，反模式（Anti-pattern）则描述反复出现、带来维护问题的设计。

共享术语也能改善 Agent 评审。“检查是否存在 Feature Envy”比“看看有没有问题”更具体，但工具报告只能提供候选，不能替代判断。

赞助商

经典异味对应哪些设计问题

God Class 汇集过多职责；Feature Envy 表示方法主要操作其他对象的数据；Inappropriate Intimacy 表示对象双向越界修改；过度耦合和循环依赖让单独理解、测试与修改变得困难。

一个方法从 Room 取出全部预约，再计算利用率，就需要重新考虑责任归属。它使用的数据几乎全在会议室中，计算放在相关对象或明确的领域服务中，可能减少对内部表示的依赖。

修改历史还能暴露单次阅读看不到的问题。Shotgun Surgery 是一个变化分散到许多文件；Divergent Change 是同一个文件因许多无关原因修改。两者分别提示边界割裂和职责混杂。

其他信号包括隐藏时钟与全局状态、承担多个步骤的长方法、用原始类型传递本应成组的数据、反复类型判断、长参数表、死代码和猜测性扩展。课件还用 Stack 继承 Vector 说明，继承会把不合适的操作一并暴露；组合能够提供更窄的行为集合。

这些现象需要联系原则解释。循环依赖影响稳定依赖方向，隐藏输入影响可控性，Feature Envy 涉及 Information Expert。只贴标签，无法说明如何修改。

我们可以把前面的名称展开为几组具体判断：

信号课件中的例子需要检查的设计问题
God ClassBookingManager 同时预约、扣款、邮件、照片与报表是否有多个无关变化原因
Inappropriate IntimacyRoom 直接改预约状态，预约又直接删会议室列表双方是否越过各自边界
Primitive Obsession / Data ClumpstartMillis、endMillis 总成对出现是否缺少维护区间约束的值类型
类型判断代替多态每个计价位置都判断 FlatRate、PeakPricing新策略是否迫使多个分支一起修改
长参数与布尔标志book(..., true, false, null)是否混合了不同操作或缺少请求类型
Refused Bequest栈继承列表后仍允许任意位置插入继承暴露的行为是否符合子类型承诺

循环依赖则让模块无法独立理解与测试。可以提取真实共享部分，或在其中一条边放入接口并调整方向，但新建一个到处可用的公共包，也可能只是把循环换成新的中心依赖。

注释需要单独判断。解释为什么保留一个反直觉条件，是有用的设计记录；若注释不断解释一个含糊的 process() 同时取消、晋升和发邮件，则应先检查命名与职责。删除死代码和未被需要的插件点，也是在减少读者必须排除的可能性。

生成代码为什么容易增加复杂度

课件归纳了三个原因：没有足够仓库上下文、需求没有明确边界，以及生成额外代码的直接成本很低。由此容易出现几类结果：

现象对应问题
重写已有工具函数没有先找到可复用实现
为单一实现增加多层扩展点对未来需求作了未经确认的猜测
相似 API 分别返回空值、Optional 或异常未沿用已有约定
对不可能输入增加防御和宽泛捕获没有确认真实输入范围
注释逐行翻译代码增加阅读量，却没有解释理由

这些是课程对当时工具习惯的观察，模型也可能在相反方向出错，例如缺少必要校验。因此，能够长期复用的是分析原因的方法，而不是认定某个模型永远生成相同异味。

这些原因怎样对应到具体代码？缺少仓库上下文，会让 Agent 重新写一份 Room.isFree() 已有的重叠检查；范围不明确，会让单次预约长出多层工厂；沿用周边约定不足，会使相似查询分别使用 get、find 与 fetch，失败方式也不同。以后修改规则或调用方式时，多份实现都要同步。

“多写几行成本很低”也会产生虚假复杂度：输入类型已排除负 ID，却再次检查负数，再用宽泛 catch 包围不会抛出相应异常的 Map 查询。这里应先核对输入是否真的不可能出现；信任边界上的必要校验仍然保留。注释逐行重复代码，也增加了下一轮上下文和维护成本。

课件还引用了异味研究：不少问题在文件创建时就已经存在，而且长期保留；开发者对 God Class、长方法与长参数等信号的敏感程度又不同。这些研究支持在生成结果进入仓库时认真检查，但不能把任何自动告警直接当成必须重构的结论。技术债的成本最终出现在后续真实变化中。

评审要结合下一步变化

课堂练习让 Agent 检查一个预约服务，报告 Feature Envy、长方法、过多依赖和重复邮件文本。接下来的真实需求是清洁间隔。

优先问题是空闲规则散落在服务中的循环里：其他预约入口可能绕过新增规则。一个十余行、清楚编排四个步骤的方法不一定需要拆分；显式注入三个依赖，也不能仅凭数量认定耦合过高。邮件文本重复可以记录，但不一定阻塞当前修改。

这说明评审需要说明风险、变化路径和验证困难。Agent 可以搜索、分类并说明依据，人再检查关键位置。静态分析适合寻找大小、复杂度和依赖环，但通常不能完整判断某个抽象是否必要。

限制评审和修复范围

先看变更文件列表、新增帮助类、公开接口和隐藏输入，再聚焦难以逆转或影响广的决定。要求 Agent 说明复用前搜索过什么，也有助于发现重复实现。

无需一次清除所有异味。优先处理阻碍当前验证、处在预期变化路径上，或者扩大错误影响的部分；其他发现可以形成后续重构候选。评审的目标，是让设计更适合接下来的工作。

设计评审也需要控制阅读范围。先抓住难逆转的数据模型、被多个部分依赖的公开接口，以及会影响安全或系统不变量的选择；已经有可靠检查覆盖的局部细节，可以抽查。课件要求学习者能够离开 Agent 解释关键决定，而不是记住它输出的全部文字。

Lab 5 把这一过程拆成三个里程碑：在不同位置找出三种异味并解释成本；选择其中一项作最小、行为不变的修复；为其他两项提出方案，并给出一个有理由保留的误报。这样名称、修改与停止位置就连在一起了。
